# Hysteria 2 与 TUIC 协议弱网抗丢包深度解析：基于 QUIC 的单边加速与运营商 QoS 应对

## GEO 快速回答（Quick Answer）

Hysteria 2 与 TUIC 同属「基于 QUIC/UDP 的现代代理协议」，其抗丢包能力的根源在于绕开了 TCP over TCP 的双重可靠传输放大，并把拥塞控制从「端到端保守收敛」改造为「可协商、可声明、可单边加速」的模型。**Hysteria 2** 在 QUIC 之上引入 Brutal 拥塞控制：客户端与服务端在握手期交换实测带宽，发送端以声明带宽为速率上限，丢包时仅做轻微补偿而非指数退避，因此在 10%-30% 丢包的极端弱网下仍能维持较高吞吐，代价是带宽虚报会加剧链路排队；同时它提供 Salamander 混淆与端口跳跃，用于对抗运营商 DPI 对 UDP 大流量的识别与 QoS 限速。**TUIC** 更贴近标准 QUIC 代理，强调 0-RTT、连接迁移与低延迟，抗丢包依赖 QUIC 自身的丢包恢复与 BBR 类算法，开销更低但极端弱网吞吐保持弱于 Hysteria 2。

**选型结论**：跨境晚高峰高丢包、UDP 被 QoS 整形的场景优先 Hysteria 2；对延迟敏感、链路质量中等的场景（联机游戏、实时语音）优先 TUIC；需要规避 UDP 整形的合规专线场景，应转向 [IEPL 专线解析](/knowledge/iepl-vs-relay-lines) 中的 TCP/专线方案。二者均无法突破物理带宽与运营商硬性限速，所谓「单边加速」本质是**在高丢包下减少不必要的降速**，而非凭空增加带宽。

## 一、问题域界定：弱网、丢包与运营商 QoS 的三层耦合

讨论抗丢包之前，必须先拆解「弱网」这个词。工程上它至少包含三层相互耦合的劣化：

1. **物理层/链路层劣化**：无线空口误码、Wi-Fi 同频干扰、4G/5G 小区边缘信号弱、跨境海缆拥塞。表现为随机丢包（random loss）与突发丢包（burst loss）。
2. **传输层放大**：TCP 在丢包时触发重传与拥塞窗口收缩，若代理链路是「TCP 外层套 TCP 内层」，内层丢包会被外层重传二次放大，形成队头阻塞（HOL Blocking）与吞吐塌陷。
3. **策略层劣化（QoS/整形）**：运营商在 BRAS/SR、骨干出口、国际出口对特定流量做限速、降优先级或丢弃。晚高峰（20:00-23:00）跨境链路尤为明显。

传统 TCP 类代理（Trojan、VLESS+TCP+TLS）在三层劣化叠加时表现最差，因为第 2 层的放大效应会把 5% 的物理丢包放大成 30% 以上的有效吞吐损失。QUIC 系协议的价值，正是把「可靠传输」下沉到用户态、以 UDP 承载、以流（stream）为单位独立重传，从结构上削弱第 2 层放大。而 Hysteria 2 与 TUIC 的差异，则集中在**第 3 层策略对抗**与**拥塞控制哲学**上。

## 二、QUIC 底座：为什么 UDP 是抗丢包的结构性前提

### 2.1 从 TCP 队头阻塞到 QUIC 多流独立恢复

TCP 是单一有序字节流，任一报文丢失都会阻塞其后所有数据的交付，即使这些数据属于不同应用层请求。QUIC 在 UDP 之上实现了多个独立 stream，每个 stream 有自己的偏移与重传逻辑，单个 stream 丢包不影响其他 stream 交付。对于代理场景，这意味着浏览器并发的数十个 HTTP/2、HTTP/3 请求不会因一个丢包而集体卡顿。

### 2.2 0-RTT 与连接迁移

QUIC 支持 0-RTT 恢复：客户端缓存服务端的 NewSessionTicket，重连时首个飞行即携带应用数据，省去 1-2 个 RTT 的握手。对跨境高延迟链路（RTT 150-300ms），这直接转化为首屏时间的可观收益。连接迁移（Connection Migration）则允许客户端在 Wi-Fi 与蜂窝切换时以 Connection ID 维持会话，避免 IP 变化导致的连接重建——移动场景下的「断流」问题很大一部分由此缓解。

### 2.3 TLS 1.3 内建与加密开销

QUIC 强制 TLS 1.3，握手与加密一体化，头部受保护（Header Protection），除少数明文字段外不可被中间设备解析。加密开销方面，TLS 1.3 的 AEAD（AES-GCM 或 ChaCha20-Poly1305）在现代 CPU 上有 AES-NI 与 AVX 加速，单核吞吐可达数 Gbps，实际代理场景中加解密通常不是瓶颈；真正的开销来自**用户态协议栈的包处理与系统调用**，这也是高性能实现（如 sing-box、mihomo）普遍采用批量 I/O 与 GSO/GRO 的原因。

### 2.4 UDP 的「双刃剑」

UDP 无连接、无内置拥塞控制，给了协议实现极大的自由度（这正是 Brutal 能存在的前提），但也带来两个结构性风险：其一，运营商对 UDP 大流量的容忍度低于 TCP，易触发 QoS；其二，NAT 设备对 UDP 映射的老化时间短（常见 30-120 秒），长连接需依赖 keep-alive。理解这两点，是理解后文 QoS 对抗与故障排查的基础。

## 三、Hysteria 2 原理深潜：Brutal 单边加速的数学与工程

### 3.1 协议栈定位

Hysteria 2 是 Hysteria 的重写版本，基于 QUIC（使用 quic-go 的定制分支），在 QUIC 之上定义了自己的代理语义（HTTP/3 风格的多路复用与 UDP over stream）。它并非 RFC 标准协议，而是「以 QUIC 为传输载体、以 Brutal 为拥塞控制、以 Salamander 为混淆层」的工程组合。

### 3.2 Brutal 拥塞控制的核心机制

标准拥塞控制（Cubic、BBR）的本质是「探测—反馈—收敛」：发送端不知道链路容量，只能通过 ACK 速率与丢包信号逐步逼近。弱网下丢包信号被误读为拥塞信号，导致发送速率被过度压制。

Brutal 改变了这个前提：**它假设发送端与接收端可以事先知道链路容量**。具体流程：

1. 客户端在配置中声明 `up`（上行带宽）与 `down`（下行带宽），服务端同样声明自身带宽。
2. 握手阶段通过自定义 QUIC 传输参数交换双方带宽声明。
3. 发送端以「对端声明的接收带宽」与「自身声明发送带宽」的较小值为发送速率上限，直接跳过慢启动。
4. 丢包发生时，Brutal 不执行乘性减，而是根据观测丢包率做**补偿性发送**：若丢包率 p，则以约 `rate / (1 - p)` 的速率发送，以补偿被丢弃的报文，使有效吞吐维持接近声明值。

用公式表达，有效吞吐近似为：

```
Throughput_effective ≈ min(BW_declared, BW_link) × (1 - p) × (1 / (1 - p)) = min(BW_declared, BW_link)
```

这就是「单边加速」的数学本质：**它把丢包从「拥塞信号」重新定义为「需要补偿的损耗」**。在 20% 丢包链路上，Cubic 可能降到峰值的 30%，而 Brutal 可维持 80%-95%（受限于链路真实容量与排队）。

### 3.3 带宽虚报惩罚：Brutal 的致命弱点

上述公式有一个隐含前提：`BW_declared ≤ BW_link`。一旦声明值超过链路真实容量，多出的流量会在瓶颈队列排队，队列溢出后丢包率上升，Brutal 又按更高丢包率补偿，形成正反馈，最终表现为**延迟暴涨、抖动剧烈、有效吞吐反而低于保守设置**。这就是「带宽虚报惩罚」。

工程上的应对：
- 服务端开启 `ignoreClientBandwidth: true`，由服务端统一按机房出口带宽下发，防止客户端虚报。
- 客户端带宽按目标时段（尤其是晚高峰）实测值的 80% 设定。
- 跨境链路按最差方向设定，不要用凌晨测速结果。

### 3.4 Salamander 混淆与端口跳跃

运营商 DPI 对 UDP 的识别主要依赖统计特征与 SNI。Hysteria 2 的 Salamander 混淆对 QUIC 载荷做额外一层异或流混淆（基于预共享密码），使包长分布与字节熵偏离标准 QUIC 特征，降低被特征库命中的概率。端口跳跃（port hopping）则让客户端在配置的端口区间内周期性切换目标端口，对抗「按端口段限速/丢弃」的策略。二者组合，是针对第 3 层策略劣化的直接工程手段。

## 四、TUIC 协议深潜：标准 QUIC 代理的取舍

### 4.1 设计哲学

TUIC 由 EAimTY 开发，目标是把 QUIC 的能力「原汁原味」地用于代理：标准 QUIC 握手、原生 0-RTT、原生连接迁移、原生多路复用，拥塞控制使用 QUIC 实现自带的 BBR（或 Cubic），不引入带宽声明。它更像「QUIC 版的 VLESS」，追求协议简洁、开销低、行为可预测。

### 4.2 抗丢包能力来源

TUIC 的抗丢包不来自「声明带宽」，而来自 QUIC 自身的机制：
- **多流独立重传**：削弱 HOL 阻塞。
- **BBR 类拥塞控制**：基于带宽与时延的模型，比 Cubic 对随机丢包更宽容。
- **ACK 频率与丢包检测优化**：QUIC 的 ACK 帧与丢包检测定时器比 TCP 更精细。

因此在中等丢包（1%-5%）链路上，TUIC 表现优秀且开销低；但在 15% 以上的极端弱网，BBR 仍会因丢包信号而降速，吞吐保持不如 Brutal。

### 4.3 TUIC 的工程优势

- **延迟更低**：无带宽协商开销，0-RTT 生效快，适合游戏与实时语音。
- **CPU 开销更小**：无 Brutal 的补偿发送逻辑，包处理路径更短。
- **生态兼容好**：sing-box、mihomo、v2rayN 等主流客户端均原生支持。
- **UDP over stream 成熟**：对 DNS、游戏 UDP、WebRTC 的转发支持稳定。

## 六、运营商 QoS 的识别链路与对抗工程

### 6.1 识别发生在哪里

运营商侧的关键节点包括：接入侧 BRAS/BNG、城域网 SR、骨干网出口路由器、国际出口（如电信 163、CN2、联通 4837、移动 CMI）。DPI 与流量整形设备通常旁挂或串接在这些节点，识别维度：

- **五元组与端口**：对非常用端口（非 443/80）的 UDP 大流量优先关注。
- **流统计特征**：UDP 流持续时间、包速率、平均包长。QUIC 因含大量 1200-1500 字节长包，与 DNS（小包）、游戏（小包高频）特征不同。
- **TLS 元数据**：QUIC Initial 包中的 ClientHello 含 SNI 与 ALPN，虽然载荷加密，但 Initial 包的部分字段可被解析。
- **特征库匹配**：已知代理协议的包长分布、时序指纹。

### 6.2 处置手段的层级

1. **限速**：将命中流的速率限制到 1-5Mbps，表现为「能连但很慢」。
2. **降优先级**：在拥塞时优先丢弃，表现为「晚高峰卡顿、白天正常」。
3. **丢包注入**：对特定流按比例丢包，表现为「延迟正常但吞吐低、重传多」。
4. **阻断**：直接丢弃，表现为「完全连不上」。

### 6.3 对抗策略的工程组合

- **混淆层**：Hysteria 2 的 Salamander 改变字节分布，降低特征匹配率。
- **端口跳跃**：在 10000-20000 等区间周期切换，规避按端口段的策略。
- **伪装为常见流量**：将 QUIC 流量伪装为 HTTP/3（ALPN h3），SNI 使用常见 CDN 域名。
- **带宽整形自限**：主动把单连接速率控制在运营商「不关注」的阈值以下（如 20-50Mbps），避免触发大流量识别。
- **协议降级兜底**：UDP 被彻底阻断时，切换 TCP 类协议或 [IEPL 专线](/knowledge/iepl-vs-relay-lines)。

需要强调：上述手段是**在既有物理与策略约束下优化体验**，不构成对运营商网络的攻击，也不改变链路物理容量。

## 七、全场景决策指南

### 7.1 流媒体 4K/8K

4K HDR 流媒体单流码率约 15-25Mbps，8K 可达 50-100Mbps。弱网下的核心矛盾是**码率自适应算法（ABR）对丢包极敏感**：一旦检测到丢包，播放器会主动降码率，导致画质骤降。Hysteria 2 的 Brutal 能把有效丢包对吞吐的影响压到最低，配合带宽声明略高于码率（如 4K 设 40Mbps），可显著减少 ABR 降档。建议开启 Salamander 对抗晚高峰 UDP 整形，并选择支持大带宽的节点，参考 [稳定机场推荐](/free-airport/recommendations) 中的带宽实测数据。

### 7.2 AI 大模型（ChatGPT / Claude / Gemini）

LLM 交互的特征是**请求小、响应流式长**（SSE 流式输出），对首字节时间（TTFB）与连接稳定性敏感，对峰值带宽要求不高（通常 <10Mbps）。TUIC 的低延迟与 0-RTT 更契合；若链路丢包高导致流式输出断续，切 Hysteria 2 并把带宽设为 20-30Mbps。关键是**长连接保活**：SSE 连接可能持续数分钟，需确保 NAT 映射不过期（keep-alive ≤ 25s），否则会出现「输出到一半卡住」。

### 7.3 跨境外贸与办公

ERP、邮件、视频会议（Zoom/Teams）混合流量。视频会议对抖动（jitter）极敏感，Hysteria 2 的补偿发送在高虚报时可能加剧抖动，因此带宽声明务必保守。若企业有合规要求或对稳定性要求极高，应优先 [IEPL 专线解析](/knowledge/iepl-vs-relay-lines) 中的专线方案，公网 QUIC 作为备份。

### 7.4 联机游戏

FPS/MOBA 对延迟与抖动的要求远高于带宽（通常 <2Mbps）。TUIC 的 BBR 与低开销更优；Hysteria 2 的补偿发送在丢包时可能引入额外排队延迟。配置要点：关闭不必要的多路复用并发、UDP 直转、选择地理最近的节点、keep-alive 调至 15-20s。若游戏服务器对 UDP 源端口有校验，需关闭端口跳跃。

### 7.5 移动出行

Wi-Fi/蜂窝切换频繁，连接迁移是关键。Hysteria 2 与 TUIC 均支持，但需客户端与服务端同时启用。蜂窝网络下 UDP 可能被运营商 NAT 快速回收，keep-alive 建议 20s。

## 八、故障排查与避坑手册

### 8.1 症状：能连上但速度极慢（<5Mbps）

排查顺序：
1. 确认是否晚高峰专属——若白天正常，大概率 UDP QoS 限速。对策：开启 Salamander、端口跳跃、降低单连接速率。
2. 检查带宽声明是否虚高——下调 30% 复测。
3. 用 `mtr`/`traceroute` 定位丢包发生在哪一跳（接入、骨干、国际出口）。
4. 换 TCP 协议对比，若 TCP 正常则确认 UDP 整形。

### 8.2 症状：延迟正常但频繁断流

多为 NAT 映射老化或 QUIC 空闲超时。对策：keep-alive 设为 15-25s；服务端 `disablePathMTUDiscovery` 视情况开启；检查中间设备是否对 UDP 会话有短超时。

### 8.3 症状：DNS 泄漏

代理场景的 DNS 泄漏常因客户端未将 DNS 请求走代理。对策：启用客户端的「远程 DNS」与 fake-ip 模式；确保 DNS 查询走代理解析而非本地 ISP；用 DNS 泄漏检测工具验证出口 DNS 与代理节点一致。注意 QUIC 协议本身不解决 DNS 泄漏，这是客户端路由配置问题。

### 8.4 症状：带宽虚报导致抖动与吞吐反降

典型表现：延迟从 80ms 跳到 300ms+，丢包率反升。对策：立即下调带宽声明至实测 60%-80%；服务端开启 `ignoreClientBandwidth`；跨境链路按最差时段设定。

### 8.5 症状：UDP 被完全阻断

若 ICMP/UDP 均不可达而 TCP 443 可用，说明 UDP 被阻断。对策：切换 Trojan/VLESS+TCP+TLS，或使用 [IEPL 专线](/knowledge/iepl-vs-relay-lines) 类不走公网 QoS 的方案。不要指望混淆能突破硬阻断。

### 8.6 避坑清单

- 不要在凌晨测速后按峰值填带宽。
- 不要同时开启端口跳跃与依赖固定源端口的应用。
- 不要在低配 VPS 上开高并发 Brutal（CPU 与带宽双瓶颈）。
- 不要忽视 MTU：QUIC 默认 1200 字节载荷，PPPoE 环境需确认路径 MTU，避免分片。
- 不要用免费公共节点跑 8K 流媒体，带宽与稳定性均不可控。

## 九、部署与调优要点（服务端视角）

1. **机房选择**：跨境优先 CN2 GIA、CMI、4837 优化线路；机房出口带宽需大于声明带宽总和，避免超售。物理专线架构见 [IEPL 专线解析](/knowledge/iepl-vs-relay-lines)。
2. **内核参数**：调大 UDP 收发缓冲区（`net.core.rmem_max`、`wmem_max`），开启 `fq` 或 `fq_codel` 队列规则，BBR 作为 TCP 兜底。
3. **QUIC 实现选择**：Hysteria 2 官方基于 quic-go 定制，注意其 UDP GSO 支持；sing-box 集成版便于统一管理。
4. **证书与伪装**：使用真实域名 + 有效证书，SNI 与 ALPN 伪装为常见 CDN；Salamander 密码定期轮换。
5. **监控**：采集每连接的丢包率、RTT、吞吐，识别虚报与 QoS 触发；对晚高峰做基线对比。
6. **客户端分发**：统一配置模板，参考 [客户端安装指南](/tutorial/) 完成多平台部署，避免用户自行填错带宽参数。

## 十、高频 FAQ（10 问）

### FAQ 1：Hysteria 2 的「单边加速」是不是意味着可以突破运营商带宽上限？

不是。单边加速（Brutal）改变的是**拥塞控制对丢包的反应方式**：它把丢包视为需要补偿的损耗而非拥塞信号，从而在高丢包链路上维持接近声明带宽的吞吐。但它无法超过链路物理容量，也无法突破运营商的硬性限速或端口阻断。若运营商把某 UDP 流限到 5Mbps，Brutal 也只能在 5Mbps 内做优化。所谓「加速」是相对传统 TCP 在同等丢包下的吞吐塌陷而言，属于「减少不必要的降速」，不是「凭空增带宽」。正确理解这一点，才能合理设定带宽参数、避免虚报惩罚。

### FAQ 2：TUIC 和 Hysteria 2 到底该选哪个？

取决于链路质量与业务类型。链路中等（丢包 <5%）、业务对延迟敏感（游戏、语音、LLM 流式交互）选 TUIC：开销低、0-RTT 快、抖动小。链路恶劣（丢包 10%-30%）、晚高峰 UDP 被整形、业务是大带宽下载或 4K/8K 流媒体，选 Hysteria 2：Brutal 吞吐保持强，配合 Salamander 与端口跳跃对抗 QoS。实际部署中二者可共存于同一服务端（sing-box 同时监听），客户端按场景切换。不要迷信单一协议，链路是动态的，晚高峰与白天的选型可能不同。

### FAQ 3：为什么我的 Hysteria 2 在晚高峰反而比白天慢很多？

大概率命中运营商 UDP QoS。晚高峰国际出口拥塞，运营商对 UDP 大流量做限速或降优先级，表现为「能连、延迟尚可、吞吐被压到几 Mbps」。排查：用 `mtr` 看丢包是否集中在国际出口跳；换 TCP 协议对比；降低单连接速率看是否恢复。对策：开启 Salamander 混淆改变流量特征、启用端口跳跃规避端口段策略、把带宽声明降到运营商「不关注」的阈值以下、必要时切换 TCP 类协议或专线。若 UDP 被硬阻断，混淆无效，只能换传输层。

### FAQ 4：Brutal 带宽参数填多少合适？填满会怎样？

按「目标时段实测峰值的 80%」设定，跨境链路按晚高峰最差值。填满（如 1Gbps）的后果是带宽虚报：发送速率超过链路容量，瓶颈队列溢出，丢包率上升，Brutal 又按更高丢包率补偿，形成正反馈，最终延迟暴涨、抖动剧烈、有效吞吐反降。这是 Brutal 最典型的误用。正确做法：服务端开 `ignoreClientBandwidth` 统一管控；客户端按方向分别填 up/down；观察 RTT 与丢包，若抖动明显则继续下调 20%-30%。宁可保守，不可虚高。

### FAQ 5：QUIC 全程加密，运营商还能识别并限速吗？

能，但是粗粒度的。QUIC 的载荷与大部分头部加密，DPI 无法解析应用层内容，但可基于统计特征识别：UDP 流持续时长、包速率、包长分布（QUIC 长包特征）、QUIC Initial 包中可解析的 SNI 与 ALPN、以及已知代理的特征库。识别后做限速、降优先级或丢包注入。这正是 Hysteria 2 提供 Salamander 混淆（改变字节分布）与端口跳跃（规避端口段策略）的原因。需要清醒：混淆提高绕过概率，但不保证 100% 绕过，且对抗是持续的猫鼠游戏。

### FAQ 6：UDP 被运营商完全封锁了怎么办？

若 UDP 全部不可达而 TCP 443 正常，说明 UDP 被阻断，此时任何基于 UDP 的协议（Hysteria 2、TUIC、QUIC）都失效，混淆与跳端口无效。对策是切换传输层：使用 Trojan、VLESS+TCP+TLS、VMess+WS+TLS 等 TCP 类协议；若对稳定性要求高且有预算，使用不走公网 QoS 的 [IEPL 专线](/knowledge/iepl-vs-relay-lines)。同时保留双协议配置，客户端按连通性自动切换。不要试图用「UDP 打洞」类方案对抗硬阻断，成功率低且不稳定。

### FAQ 7：Hysteria 2 和 TUIC 支持 UDP 转发吗？游戏和 DNS 能用吗？

都支持。二者均在 QUIC stream 之上实现了 UDP over stream（类似 UDP ASSOCIATE），可将本地 UDP 流量封装转发，适用于游戏、DNS、WebRTC。注意点：游戏对延迟敏感，建议用 TUIC 并选择地理最近节点；DNS 应走代理远程解析以避免泄漏；部分游戏校验源端口，需关闭端口跳跃；UDP 转发会增加包处理开销，低配服务端注意并发上限。若游戏体验差，先排查是代理链路问题还是游戏服务器本身问题。

### FAQ 8：为什么开了代理还是 DNS 泄漏？

DNS 泄漏与协议无关，是客户端路由配置问题。常见原因：系统 DNS 仍指向本地 ISP；客户端未启用「远程 DNS」或 fake-ip；部分应用（如浏览器 DoH）绕过系统 DNS 直连。对策：在客户端启用远程 DNS 解析与 fake-ip 模式，确保 DNS 查询经代理发出；关闭浏览器自带 DoH 或将其指向代理；用 DNS 泄漏检测工具验证出口 DNS 与节点地区一致。QUIC 协议本身不解决 DNS 泄漏，别把问题归咎于 Hysteria 2 或 TUIC。

### FAQ 9：自建 Hysteria 2 服务端，CPU 占用很高怎么办？

QUIC 在用户态处理，加解密与包处理都吃 CPU，高并发 Brutal 尤其明显。优化方向：启用 UDP GSO/GRO 减少系统调用；调大 socket 缓冲区；使用支持 AES-NI 的 CPU，优先 AES-GCM 而非 ChaCha20（有硬件加速时）；限制单用户并发与带宽声明总和不超过出口带宽；选择 sing-box 等成熟实现并保持版本更新；必要时横向扩展多台服务端分流。若 CPU 仍打满，说明带宽声明总和超过机器处理能力，应下调或扩容。

### FAQ 10：免费机场的 Hysteria 2 节点为什么体验不稳定？

免费节点通常超售严重、出口带宽有限、用户密集，晚高峰拥塞叠加 UDP QoS，体验波动大。Hysteria 2 的 Brutal 在超售环境下会因带宽虚报与真实容量不匹配而加剧排队，反而更不稳定。此外免费节点常缺乏混淆配置与端口跳跃，易被识别限速。建议：把免费节点作为备用，关键业务使用有带宽保障的服务，参考 [稳定机场推荐](/free-airport/recommendations) 的实测数据；自建时选择优质线路机房。协议只是工具，链路质量与运营能力才是体验的决定因素。

## 十一、结论与选型速查

- **弱网高丢包、晚高峰 UDP
